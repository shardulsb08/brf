# BRF architecture and its lift to protocol-flow fuzzing

**Read this when:** designing any extension to BRF that introduces a new
pseudo-syscall family (e.g. for MPTCP, in-kernel QUIC, NET_HANDSHAKE),
or evaluating whether a fuzzing goal fits the BRF model.

**Companion document:** Shardul's `docs/bpf_program_generator/
BPF_Program_Generator_Deep_Dive_Analysis.md` (tracked) covers the same
ground from the inside of the eBPF generator; this file describes the
generalizable architecture and the recipe for extending it.

**Status:** Drafted 2026-05-15 from a code walk of `prog/brf.go`,
`prog/brf_legacy.go`, `prog/brf_prog.go`, `executor/common_brf_linux.h`,
`sys/linux/bpf.txt`, and Hung+Sani's papers (arXiv:2305.08782, ACM
PACMSE 1(FSE) Art. 52).  Updated when the architecture changes.

## 1. The three-plane architecture

BRF extends Syzkaller along three planes that meet at the pseudo-
syscall boundary:

```
        SYZLANG PLANE  (sys/linux/bpf.txt)
        --------------
        syz_bpf_prog_open(path ptr[in, string])
        syz_bpf_prog_load(path ptr[in, string], res ptr[out, bpf_res]) fd_bpf_prog
        syz_bpf_prog_attach(path ptr[in, string]) fd_bpf_link
                                |
                                | (consumed by syz-sysgen)
                                v
        EXECUTOR PLANE  (executor/common_brf_linux.h)
        --------------
        static long syz_bpf_prog_open (volatile long a0)             { ... }
        static long syz_bpf_prog_load (volatile long a0, ... a1)     { ... }
        static long syz_bpf_prog_attach(volatile long a0)             { ... }
                                |
                                | (registered into dispatch table)
                                v
        executor/syscalls.h:8917-8919  (auto-generated by syz-sysgen)
                {"syz_bpf_prog_open",   ..., (syscall_t)syz_bpf_prog_open},
                {"syz_bpf_prog_load",   ..., (syscall_t)syz_bpf_prog_load},
                {"syz_bpf_prog_attach", ..., (syscall_t)syz_bpf_prog_attach},

        GENERATOR PLANE  (prog/brf.go, brf_legacy.go, brf_types.go)
        ---------------
        BpfRuntimeFuzzer {                          (prog/brf.go:12)
            isEnabled     bool
            workDir       string
            helperFuncMap map[string]*BpfHelper
            progTypeMap   map[BpfProgTypeEnum]*BpfProgType
            ctxAccessMap  map[BpfProgTypeEnum]*BpfCtxAccess
        }
        GenPrologue(r, s, prog) ->                  (prog/brf.go:86)
            genSeedBpfProg(r)         -> compiles C to .o on disk
            append syz_bpf_prog_open  (path = .o file)
            append syz_bpf_prog_load  (path, &res)
            append syz_bpf_prog_attach(path)
            append bpf$BPF_PROG_TEST_RUN(res.prog_fds[0])
```

The genius of the pattern: **the generator plane never expresses the
complex object directly**.  It writes a compiled artifact (the `.o`
file) to disk, then emits *four small syscalls* that reference that
artifact by path.  The executor plane loads the artifact via libbpf
and threads kernel-side state (prog_fds, map_fds) back through the
`bpf_res` out-parameter so subsequent syscalls can use those file
descriptors.

This separation is what makes BRF tractable.  Random syzlang cannot
produce a verifier-clean eBPF program; rather than try, BRF generates
the program in a different representation (C source compiled with
LLVM) and feeds the result into syscalls that *do* fit syzlang.

## 2. The pseudo-syscall lifecycle (end-to-end, one example)

Concrete example: `syz_bpf_prog_load`, the load step.

### 2a. Syzlang declaration  (`sys/linux/bpf.txt:96`)

```
syz_bpf_prog_load(path ptr[in, string], res ptr[out, bpf_res]) fd_bpf_prog
```

This declares:
- Name: `syz_bpf_prog_load`
- Two arguments: a string path (input pointer) and a `bpf_res` struct
  (output pointer).
- Return type: `fd_bpf_prog` (a Syzkaller resource type; the returned
  fd flows into subsequent syscalls that take this resource).

The `bpf_res` struct is declared right below at `bpf.txt:100`:

```
bpf_res {
    prog_fds  array[fd_bpf_prog, 32]
    prog_num  len[prog_fds, int32]
    map_fds   array[fd_bpf_map, 32]
    map_num   len[map_fds, int32]
}
```

This is the state-carrier between the load step and any later step
that needs the file descriptors.

### 2b. Executor implementation  (`executor/common_brf_linux.h:62-93`)

```c
static long syz_bpf_prog_load(volatile long a0, volatile long a1)
{
    const char *file       = (char *)a0;
    struct bpf_res *res    = (struct bpf_res *)a1;
    struct bpf_program *prog;
    struct bpf_object  *obj;
    struct bpf_map     *map;
    int i, err;

    obj = find_bpf_object_by_basename(file);          /* lookup */
    if (!obj) { ... return -1; }

    bpf_object__add_kcov_handle(obj, kcov_common_handle());
    err = bpf_object__load(obj);                       /* libbpf does heavy lifting */
    if (err) { ... return -1; }

    i = 0;
    bpf_object__for_each_program(prog, obj)
        res->prog_fds[i++] = bpf_program__fd(prog);    /* fill out-param */

    i = 0;
    bpf_object__for_each_map(map, obj)
        res->map_fds[i++] = bpf_map__fd(map);

    return res->prog_fds[0];
}
```

Note three patterns:

1. **Heavy lifting outsourced** to a library (`libbpf` here).  BRF
   does not reimplement ELF relocation.  Same pattern would apply if
   protocol harnesses outsourced TLS bytes to a small embedded
   TLS lib, or HMAC computation to OpenSSL.
2. **Side-effect storage in static array.**  `find_bpf_object_by_basename`
   looks up against `bpf_object_list[OBJ_LIST_SIZE]` declared at
   line 4.  The Open step populated this array; the Load step
   consults it.  In-executor static state is how BRF carries data
   between pseudo-syscalls without round-tripping through syzlang
   resource types.  Tradeoff: simpler descriptions; harder to fuzz
   the linkage itself.
3. **Out-parameter for kernel-side handles.**  `res->prog_fds[]`
   and `res->map_fds[]` are filled in C, then syzlang treats the
   `bpf_res` as the source-of-truth for subsequent `fd_bpf_prog`
   and `fd_bpf_map` resources.

### 2c. Dispatch registration  (`executor/syscalls.h:8918`, auto-generated)

```c
{"syz_bpf_prog_load", 0, {}, (syscall_t)syz_bpf_prog_load},
```

This file is regenerated by `syz-sysgen` whenever syzlang descriptions
change.  Not hand-edited.

### 2d. Generator emission  (`prog/brf.go:111-114`)

In `GenPrologue`:

```go
c1 := genBpfProgLoadCall(r, s, p)
s.analyze(c1)
prog.Calls = append(prog.Calls, c1)
```

`genBpfProgLoadCall` constructs a `*prog.Call` from `r.target.SyscallMap
["syz_bpf_prog_load"]`, fills the path argument with the on-disk `.o`
file (whose name comes from `BpfProg.BasePath`), and lets the runtime
allocate the `bpf_res` output buffer.

The full prologue emits four calls in fixed order (`prog/brf.go:106-124`):

```
genBpfProgOpenCall    -> syz_bpf_prog_open    (path)
genBpfProgLoadCall    -> syz_bpf_prog_load    (path, &res)
genBpfProgAttachCall  -> syz_bpf_prog_attach  (path)
genBpfProgTestRunCall -> bpf$BPF_PROG_TEST_RUN(prog_fds[0])
```

The last call is a *real* BPF syscall (not a pseudo-syscall) that
triggers execution of the loaded program.

## 3. The orchestrator: BpfRuntimeFuzzer

`prog/brf.go:12-19` defines the orchestrator:

```go
type BpfRuntimeFuzzer struct {
    isEnabled     bool
    workDir       string                              // on-disk staging area
    helperFuncMap map[string]*BpfHelper               // all helpers
    progTypeMap   map[BpfProgTypeEnum]*BpfProgType    // per-prog-type
    ctxAccessMap  map[BpfProgTypeEnum]*BpfCtxAccess   // per-prog-type
}
```

It owns three pieces of domain knowledge that come from analysing the
kernel statically (`prog/brf_types.go`, 2103 lines of static tables):

- **`helperFuncMap`**: every BPF helper (4xx of them) keyed by name,
  with arg types, return types, and which prog types may call it.
- **`progTypeMap`**: every prog type, with its allowed helpers, its
  attach hook(s), its trigger mechanism.
- **`ctxAccessMap`**: per-prog-type rules for what `ctx->field` reads
  are legal (matches kernel's `is_valid_access` callbacks).

Initialization is at `prog/brf_legacy.go:1902 InitFromSrc()`, fed from
the static tables generated by Hung+Sani's verifier-analysis pipeline.

Key entry points (called by Syzkaller's `prog/generation.go:25`):

- `GenPrologue(r, s, prog)` (`brf.go:86`) — emit the 4-syscall
  prologue at the head of each fuzz input.
- `genSeedBpfProg(r)` (`brf.go:219`) — generate + compile a seed eBPF
  program.  Calls `GenBpfProg` inside (`brf_legacy.go:2441`).
- `mutSeedBpfProg(r, path)` (`brf.go:265`) — mutate an existing seed
  for corpus evolution.  Calls `MutBpfProg` (`brf_legacy.go:2459`).
- `compileBpfProg(p)` (`brf.go:313`) — runs clang to compile the C
  source to a `.o` file on disk.

## 4. The state-carrier pattern

BRF threads kernel-side state from syscall to syscall through three
mechanisms:

1. **Syzkaller resource types**: `fd_bpf_prog`, `fd_bpf_map`,
   `fd_bpf_link`.  Returned by one syscall, consumed by another.
   Syzkaller's choice tables and resource tracker keep this
   linkage tight.
2. **Out-parameter structs**: `bpf_res`.  The struct's fields are
   declared with resource element types (`array[fd_bpf_prog, 32]`),
   so anything the executor writes into the out-param ends up in the
   resource pool.
3. **Static in-executor storage**: `bpf_object_list[OBJ_LIST_SIZE]`
   carries the libbpf object across the Open->Load->Attach trio.
   Not visible to syzlang at all.

The first two are state that *syzlang can mutate*.  The third is
state that *syzlang takes as given*.  For protocol harnesses this
distinction will matter: cryptographic material we want to mutate
(keys, nonces) goes through resource-typed out-params; book-keeping
that should remain consistent (socket pairs, connection contexts)
goes into static executor storage.

## 5. The reference-acquire/release pattern (BRF layer L3e)

For eBPF, BRF tracks helper-call acquire/release pairs (ringbuf
reserve/submit, socket lookup/release).  When the generator emits an
acquire, it immediately or near-immediately emits the matching
release within the same eBPF program, to satisfy the verifier's
"reference leak" check.

Code: `prog/brf_legacy.go` around the helper-call recursion at
line ~1991 and the reference tracker described in Hung+Sani Sec 4.5.

**This is the load-bearing pattern for protocol-flow fuzzing.**  The
analogue across protocols:

| eBPF acquire/release | Protocol acquire/release          |
|----------------------|-----------------------------------|
| `bpf_ringbuf_reserve` / `_submit` or `_discard` | MPTCP `ADD_ADDR` / `RM_ADDR`     |
| `bpf_sk_lookup_tcp`  / `bpf_sk_release`         | QUIC `NEW_CONNECTION_ID` / `RETIRE_CONNECTION_ID` |
| `bpf_skb_load_bytes` / (read-only, no release)   | TLS `NEW_TOKEN` / consumption     |
| Map element refcounts                            | MPTCP token registration / cleanup |

For each, the dependency between acquire and release is enforced by
the generator: a token issued in step N must be referenced and
eventually retired by step N+k.  This is what no other published
syzkaller fork does for transport protocols.

## 6. What's eBPF-specific vs reusable

| Layer                                  | Reusable for protocols?                                                          |
|----------------------------------------|----------------------------------------------------------------------------------|
| Three-plane separation (syzlang/exec/gen) | **Reusable verbatim**.                                                       |
| Pseudo-syscall + out-param state-carrier | **Reusable verbatim**.                                                       |
| Static domain-knowledge tables (helpers, types, ctx access) | **Reusable as pattern**; rebuild tables from MPTCP option spec, QUIC frame types, TLS handshake messages instead of BPF verifier. |
| C-source-level program generation (LLVM compile) | **Drop**.  Protocols don't have a program-vs-syscall distinction.       |
| Reference acquire/release pairing      | **Reusable as pattern**; remap to protocol-level acquire/release (tokens, conn IDs). |
| libbpf load delegation                 | **Drop**.  Protocols don't have a libbpf equivalent at the kernel boundary.     |
| BPF_PROG_TEST_RUN trigger              | **Reusable as pattern**; remap to "drive state machine to depth N".             |
| kcov remote-coverage instrumentation   | **Reusable verbatim**; instrument `tcp_in`, `mptcp_pm_*`, `quic_*`, `tls_*`     |
| BTF integration                        | **Drop**.  eBPF-specific.                                                       |

## 7. Recipe: how to add a new pseudo-syscall family

When extending BRF for a new subsystem (e.g. MPTCP), the work is in
the same three planes, in roughly this order:

### Step 1: Define the state-carrier (syzlang)

In a new file `sys/linux/socket_mptcp_crypto.txt` (or similar), declare
the state-carrier struct and any resource types:

```
resource mptcp_state[intptr]
mptcp_state_token { value int32 }

mptcp_state_carrier {
    token        int32
    local_key    int64
    remote_key   int64
    local_nonce  int32
    remote_nonce int32
    /* ... whatever the harness needs ... */
}
```

### Step 2: Declare the pseudo-syscalls (syzlang)

```
syz_mptcp_pair_init(local_addr ptr[in, sockaddr_storage],
                    remote_addr ptr[in, sockaddr_storage],
                    state ptr[out, mptcp_state_carrier]) mptcp_state

syz_mptcp_join_subflow(state mptcp_state,
                       addr_idx int8,
                       backup_flag flags[mptcp_join_flags, int8])

syz_mptcp_drive_traffic(state mptcp_state,
                        data ptr[in, array[int8]],
                        len bytesize[data, int32])
```

Resource type `mptcp_state` ties the calls together: `pair_init`
returns one, the others consume it.

### Step 3: Implement the executor side (C)

In `executor/common_brf_linux_mptcp.h` (new), include the
implementations:

```c
struct mptcp_state {
    int      server_fd;
    int      client_fd;
    uint32_t token;
    uint64_t local_key;
    uint64_t remote_key;
    uint32_t local_nonce;
    uint32_t remote_nonce;
    bool     established;
};

#define MPTCP_STATE_POOL_SIZE 16
static struct mptcp_state mptcp_state_pool[MPTCP_STATE_POOL_SIZE];

static long syz_mptcp_pair_init(volatile long a0, volatile long a1,
                                volatile long a2)
{
    /* 1. socket() both endpoints with IPPROTO_MPTCP
       2. bind / listen / connect
       3. capture local_key (from setsockopt MPTCP_INFO or by
          peeking the TCP option from a tap)
       4. derive token = SHA1(key) truncated
       5. store everything in mptcp_state_pool[i]
       6. write the captured material into the out-param
       7. return pool index as the resource handle               */
}

static long syz_mptcp_join_subflow(volatile long a0, volatile long a1,
                                   volatile long a2)
{
    /* 1. lookup state by pool index
       2. generate local_nonce
       3. compute HMAC = HMAC-SHA256(
              key = local_key||remote_key,
              msg = local_nonce||remote_nonce)
       4. craft MP_JOIN SYN option bytes
       5. inject the packet (via raw socket, AF_PACKET, or tun fd) */
}
```

Include the new header from `executor/common_linux.h` under a fresh
`SYZ_HAS_MPTCP_HARNESS` feature flag.

### Step 4: Wire into the orchestrator (Go)

Two choices:

(a) **Extend GenPrologue** to optionally emit MPTCP prologue calls
    when a special program type or feature flag is requested.

(b) **Define a sibling orchestrator** (`MptcpFlowFuzzer` next to
    `BpfRuntimeFuzzer`) that owns its own state and is invoked
    independently from `prog/generation.go`.

Option (b) is cleaner architecturally and matches the brief's
"sibling fuzzers" framing.  Option (a) is faster to prototype.
Recommendation: start with (a) under a feature flag to validate the
descriptions; refactor to (b) once the design solidifies.

### Step 5: Domain-knowledge tables

For MPTCP specifically, the tables BRF builds for eBPF have analogues:

| BRF table          | MPTCP analogue                                            |
|--------------------|-----------------------------------------------------------|
| `helperFuncMap`    | `optionMap`: every MPTCP suboption + its byte layout      |
| `progTypeMap`      | `flowTypeMap`: handshake-only vs subflow-add vs DSS-data  |
| `ctxAccessMap`     | `statefulFieldMap`: which fields of state are mutable per flow type |

These tables drive what `MutBpfProg` does in the eBPF case; the
protocol analogue is what mutates the MP_JOIN flag bytes, the nonce
choices, etc., without breaking the dependency between captured
material and on-wire bytes.

### Step 6: Add kcov instrumentation hooks (kernel-side patch)

BRF needs kernel-side patches so coverage from kernel execution
points (the eBPF program runtime; for us, protocol-state-machine
entry points) feeds back to the fuzzer.  This is BRF's layer L7
(runtime coverage feedback), and the BRF paper mentions it in
passing as "kernel modifications required."  Shardul has authored
the implementation as three patches, currently at version v06:

```
/mnt/work_4gb/Tools/003_kernel_testing/prana_kernel_testing/
  container_kernel_workspace/kernel_patches/ebpf/brf/kcov_for_bpf/v06/
    0001-kcov-bpf-Add-support-for-preallocated-coverage-area.patch
    0002-bpf-Add-BRF-coverage-collection-support-via-kcov-rem.patch
    0003-bpf-Support-getting-kcov_remote_handle-using-bpf_pro.patch
```

What each patch does:

1. **0001 (general-purpose, reusable as-is).**  Adds
   `kcov_remote_start_prealloc()` and `kcov_remote_stop_prealloc()`
   variants to `kernel/kcov.c` + `include/linux/kcov.h`.  The
   existing `kcov_remote_start()` uses `vmalloc()` which can sleep,
   so it cannot be called from interrupt context.  The prealloc
   variants accept caller-owned memory, making them safe in any
   context.  **This patch is subsystem-agnostic** and applies
   unchanged to any future protocol-harness work that needs in-IRQ
   or in-atomic coverage collection.
2. **0002 (eBPF-specific; the pattern transfers).**  Wires kcov
   into BPF: adds `kcov_remote_handle`, `kcov_coverage_area`, and
   `kcov_area_size` to `struct bpf_prog` (`include/linux/bpf.h`);
   wraps `__bpf_prog_run()` in `kcov_remote_start_prealloc()` /
   `kcov_remote_stop_prealloc()` calls (`include/linux/filter.h`);
   extends `union bpf_attr` and libbpf's `bpf_prog_load_opts` to
   pass the handle from userspace.  The pattern -- add handle +
   prealloc area to subsystem struct, wrap entry point, extend
   uapi -- is what we replicate for protocol subsystems.
3. **0003 (eBPF-specific).**  Exposes `kcov_remote_handle` via
   `struct bpf_prog_info` so userspace can confirm coverage is
   enabled on a loaded program.  Pattern reusable if a protocol
   harness needs the same visibility (probably not for our v1).

For protocol harnesses, the analogous instrumentation points are:

- `tcp_v4_rcv` / `tcp_v6_rcv` for MPTCP subflow input
- `mptcp_pm_*` for path-manager events
- `quic_packet_rcv` for QUIC packet receive
- `tls_rx_one_record` for kTLS receive
- `handshake_*` (in `net/handshake/`) for NET_HANDSHAKE

For each subsystem, the recipe is:
1. Reuse patch 0001 verbatim (it lives in `kernel/kcov.c`, not in
   any subsystem-specific code).
2. Author a per-subsystem analogue of patch 0002 that adds a
   kcov handle to the subsystem's per-flow state struct (per-msk
   for MPTCP, per-quic-sock for QUIC, per-handshake_req for tlshd)
   and wraps the chosen entry points with the prealloc calls.
3. Add 0003-style uapi exposure only if the harness needs to
   verify coverage from userspace.

**Reference status (2026-05-15):** patches v06 are believed to
work but not 100% verified.  Reuse them as-is for any BRF revival
work on eBPF.  For protocol-harness work, treat 0001 as
load-bearing prior art and re-derive 0002/0003 for the target
subsystem.  See also project memory
`reference_kcov_brf_patches.md` for the patch-set version history.

**How patches relate to the kernel base:** patches live in the BRF
repo (`brf/kernel_patches/<harness>_kcov/v??/`), not in the kernel
tree.  At build time, we fetch upstream, fast-forward our local
tracking branch (`*_brf_fuzz_base`), then apply our patches.  This
keeps the kernel tree upstream-clean for diffs and reproduction,
and lets the kernel base move forward without breaking our patch
series.  Full workflow:
`.claude/designs/kernel_base_management.md`.

## 8. The lift to protocol-flow fuzzing (architectural sketch)

```
        SYZLANG PLANE  (new files under sys/linux/)
        --------------
        socket_mptcp_crypto.txt       (MPTCP MP_JOIN harness)
        socket_quic_handshake.txt     (in-kernel QUIC, later)
        socket_handshake_ktls.txt     (NET_HANDSHAKE + kTLS coupling)
                                |
                                v
        EXECUTOR PLANE  (new headers under executor/)
        --------------
        common_brf_linux_mptcp.h      (syz_mptcp_*)
        common_brf_linux_quic.h       (syz_quic_*)
        common_brf_linux_handshake.h  (syz_handshake_*)
                                |
                                v
        GENERATOR PLANE  (new Go files under prog/)
        ---------------
        Option (a): extend BpfRuntimeFuzzer.GenPrologue with a switch
                    on a target-subsystem feature flag.
        Option (b): MptcpFlowFuzzer, QuicFlowFuzzer, HandshakeFuzzer
                    as siblings to BpfRuntimeFuzzer.

        Either way: a per-subsystem analogue of helperFuncMap /
        progTypeMap / ctxAccessMap drives generation and mutation.
        Acquire/release pairing (token/HMAC, conn-ID issuance/retirement,
        handshake-DONE/kTLS-install) is the load-bearing extension.
```
